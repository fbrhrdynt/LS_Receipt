## Verification scope

This audit is based on source inspection of the current GitHub main branch. The public site could not be fetched from the available web runner, so I am not claiming a browser click-through or runtime PASS. Per R-35, runtime verification must happen after approved fixes are deployed and built.

## Findings

### 1. HIGH - R-37: No positive design direction is documented
There is no DESIGN.md or equivalent design direction in the repository. "Do not look AI-generated" is a filter, not a visual identity. The current design therefore has no documented basis for color, typography, layout rhythm, or motion.

Evidence:
- No DESIGN.md in the repository.
- No AGENTS.md, CLAUDE.md, or GEMINI.md with an antislop pointer.

Fix:
- Before visual redesign, define a short design direction for Receipt Generator: identity, mood, palette, typography, and ENERGY/RHYTHM/MOTION dials.

### 2. HIGH - R-34, R-21: Dark mode foundation is incomplete
ThemeContext correctly adds light/dark classes, but the page root does not consistently use the theme tokens. The body has no bg-background or text-foreground style, so dark pages can still inherit the browser's white background. ReceiptHistory has no theme background at all, and ReceiptGeneratorPage uses a translucent bg-muted/10 layer that can reveal the white body behind it.

Evidence:
- apps/web/src/index.css: body only sets font-family and overflow-x.
- apps/web/src/pages/ReceiptHistory.jsx: top-level page has no bg-background.
- apps/web/src/pages/ReceiptGeneratorPage.jsx: top-level page uses bg-muted/10.

Fix:
- Apply background and foreground theme tokens at body/root level.
- Add matching color-scheme handling for native controls.
- Verify Home, Generator, History, dialogs, selects, date/time inputs, and receipts in both themes.

Note:
- White receipt paper in preview is intentional and should remain white in dark mode.

### 3. HIGH - R-34: Toast theme is disconnected from the app theme
The app uses a custom ThemeContext, but Sonner imports useTheme from next-themes. There is no next-themes ThemeProvider in App.jsx, so toast appearance can disagree with the visible app theme.

Evidence:
- apps/web/src/contexts/ThemeContext.jsx: custom theme state.
- apps/web/src/components/ui/sonner.jsx: imports useTheme from next-themes.
- apps/web/src/App.jsx: no next-themes ThemeProvider.

Fix:
- Use the existing custom ThemeContext in Sonner, or move the entire app consistently to one theme provider.

### 4. HIGH - R-03, R-24: Mobile navigation and tap targets are incomplete
The desktop navigation is hidden below md and no mobile navigation replaces it. Mobile users cannot navigate to Generator or History from the header. Several controls are also below the 44px minimum tap target required by R-03.

Evidence:
- Header.jsx: nav uses hidden md:flex with no mobile menu.
- Header theme button: h-9 w-9.
- Header language trigger: h-9.
- Export buttons use size="sm", which maps to h-8.
- Receipt item editor uses grid-cols-4 at every breakpoint.

Fix:
- Add a compact mobile navigation.
- Raise important tap targets to at least 44px.
- Reflow item fields on narrow screens instead of forcing four columns.

### 5. HIGH - R-26: History Filter button is a dead control
The Filter button is rendered as interactive UI but has no onClick, no menu, and no filtering behavior.

Evidence:
- apps/web/src/pages/ReceiptHistory.jsx: Filter button has no action.

Fix:
- Implement the filter UI, or remove the button until the feature exists.

### 6. HIGH - R-24, R-20: Old febroherdyanto.web.id references remain
The active application still references the previous domains. This conflicts with the requested migration to febro.id.

Evidence:

  https://receipt.febroherdyanto.web.id/

### 7. HIGH - R-26, R-35: Print is not reliable for React templates
printReceipt copies only the receipt element innerHTML into a new blank window. The new window does not load the app's Tailwind stylesheet or fonts. React templates depend heavily on classes, so printed output can lose layout and typography. Classic templates survive better because much of their styling is inline.

Evidence:
- apps/web/src/utils/ReceiptExport.jsx: print window writes element.innerHTML and only a tiny local style block.

Fix:
- Print using a document that includes the compiled stylesheet, or copy the active styles into the print window before printing.

### 8. HIGH - R-27, R-35: History data has no error state and localStorage parsing is unguarded
History has an empty state, but it has no error state. JSON.parse is used directly in both History and Generator. Corrupt or incompatible localStorage data can crash the screen.

Evidence:
- ReceiptHistory.jsx: JSON.parse(localStorage.getItem('receipts') || '[]')
- ReceiptGeneratorPage.jsx: same pattern during autosave.

Fix:
- Add safe parsing, schema fallback, and a visible recovery/error state.

### 9. HIGH - R-35: Autosave can create duplicate history entries
When storeName is set but orderId is empty, every form change can create another saved receipt because matching only occurs when orderId is truthy.

Evidence:
- ReceiptGeneratorPage.jsx:
  findIndex checks r.orderId === formData.orderId && formData.orderId
  but the insert condition allows formData.storeName without an orderId.

Fix:
- Give the current draft a stable internal ID and update that record until the user explicitly duplicates or starts a new receipt.

### 10. HIGH - R-26, R-35: Language switching is incomplete
The language control changes translated keys, but several visible strings remain hardcoded in English. This makes the language toggle only partially functional.

Evidence includes:
- Footer.jsx: "Professional receipt generation made simple", "Product", "Author", copyright.
- ReceiptGeneratorPage.jsx: "Configure and customize your thermal receipt".
- ReceiptHistory.jsx: "View and manage your saved thermal receipts" and mixed-language dialog text.
- HistoryItem.jsx: English fallback labels such as "Unnamed Store" and "No Order ID".
- Some Classic template labels are inherited from the legacy renderer and remain English.

Fix:
- Move app-level visible copy into locale files.
- Keep Classic template layout unchanged; only translate labels if approved separately.

### 11. HIGH - R-38: Random sample identities look real
RandomGenerators contains realistic names, including names associated with real public figures. Those names can be inserted into an exported receipt without a visible sample/demo label.

Evidence:
- apps/web/src/utils/RandomGenerators.jsx includes names such as Siti Nurhaliza, Ayu Ting Ting, Bambang Pamungkas, and Dian Sastro.

Fix:
- Use clearly synthetic sample names such as "Pelanggan 001", "Kasir A", and "Toko Contoh", or visibly mark generated data as sample until the user edits it.

### 12. HIGH - R-35: The HTML references a favicon that does not exist
index.html requests /vite.svg, but no vite.svg or replacement favicon exists in the repository.

Evidence:
- apps/web/index.html: href="/vite.svg"
- Repository tree: no vite.svg.

Fix:
- Add an approved Receipt Generator favicon, or remove the broken reference until an asset is supplied.

### 13. MEDIUM - R-01, R-04, R-10, R-12, R-19, R-31: Home page contains a dense AI-slop technique cluster
The landing page combines multiple default AI visual techniques without documented purpose: four-color radial mesh gradients, glassmorphism, a decorative Sparkles icon, a gradient line, very large rounding, heavy shadows, hover lift, and fade-up entrance motion. Header, hero card, and footer all use glass-panel.

Evidence:
- index.css: mesh-bg uses blue, purple, green, and pink radial gradients.
- index.css: glass-panel uses backdrop blur and large shadow.
- HomePage.jsx: Sparkles, rounded-[2.5rem], shadow-2xl, gradient top line, Framer fade-up.
- Header.jsx and Footer.jsx also use glass-panel.

Fix:
- After design direction is approved, remove techniques that do not serve a specific hierarchy or product identity purpose.
- Keep only effects with a written reason.

### 14. LOW - R-05: Footer uses a generic template structure and leaves an empty grid column
Footer declares md:grid-cols-4 but renders only three groups. The structure is also a generic Product/Author footer pattern rather than content-driven composition.

Evidence:
- apps/web/src/components/Footer.jsx: md:grid-cols-4 with three child sections.

Fix:
- Use a deliberate 2 or 3 column structure based on actual footer content.

## Dark mode summary

The receipt preview itself should remain white because it represents paper. The dark-mode defect is in the application shell and theme plumbing, not the paper preview.

Primary dark-mode fixes:
- body/root must use theme background and foreground tokens.
- Sonner must use the same ThemeContext as the rest of the application.
- Native inputs should receive the matching color-scheme.
- Recheck History modal staging area and all interactive components in both themes.
